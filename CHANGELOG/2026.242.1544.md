# 2026.242.1544 — feat(WP4): runtime resize over a control socket

## Summary

WP4's runtime resize: a control surface that rewrites the `size` capsfilter a resize targets, with
the clamping and rate limit the plan specifies.

**A line-oriented Unix socket, not a resize-shaped entry point.** Every other control the
architecture lists — `stats`, `volume`, `clipboard`, `idle` — needs the same seam, and inventing a
private one per control is how a stack ends up with four. It also has to be able to **reply**, which
a signal or a sentinel file cannot: a resize that silently clamps is the exact failure mode this
package exists to make visible.

```
$ printf 'resize 1600 900\n' | socat - UNIX-CONNECT:/tmp/cstream-control.sock
OK resize 1600x896
```

## The finding: the plan's own WP4 gate names a size that cannot apply

The plan's gate says *"1600×900, 3840×2160 and 640×480, each asserting `wl: hypr-monitors` reports
the requested size."*

`Geometry::sanitised()` rounds to a multiple of 8, and **900 is not one**: `900 & !7 = 896`. So
`1600×900` applies as **`1600×896`**, and a gate asserting the *requested* 900 would fail against
entirely correct behaviour. `3840×2160` and `640×480` are both fine — all four values are multiples
of 8.

This is the same trap the plan warns about from the other side. It correctly says *"asserting 'no
error' proves nothing here — the 1280×720 snap is silent"*, and the remedy is to assert the actual
size; but one of the three sizes it chose to assert is one the code legitimately changes.

That is why `Control::resize` returns the geometry **actually applied** rather than `()`, and why
the socket reply names what landed rather than echoing the request. A caller that assumes otherwise
writes precisely the gate that fails.

## What is here

```
control.rs   Control{resize,current} + the socket server, bind(), socket_path()  (new)
lib.rs       pub mod control;
main.rs      the listener, wired into the SERVING path only
```

- **Rate limit** — 500 ms between *applied* resizes (the plan's 2/s). A caps renegotiation tears
  down and rebuilds the encoder's input, so a client resizing on every pointer motion during a drag
  would spend the drag renegotiating and deliver nothing.
- **No-op resizes are exempt** from the limit: they apply nothing, so they cannot cost a
  renegotiation, and refusing them would make an idempotent retry look like a failure.
- **`OK …` / `ERR …` replies** so a check step can assert on what applied rather than on an exit
  status that says nothing about it.
- **Stale-socket removal on bind** — a leftover socket file from a crashed run makes `bind` fail
  with `EADDRINUSE`, which reads as "already running" when nothing is.
- **The listener opens only on the serving path, after PLAYING.** Opening it earlier would advertise
  a control surface for a graph that may still fail to negotiate, and `--probe` must not leave a
  socket behind for the next run to trip over. It runs on its own thread because the bus loop below
  blocks with no timeout.
- **A socket that cannot bind is reported loudly but is not fatal.** A stream that cannot be resized
  is still a stream; killing the session over its control channel would be the worse failure.

The nine new tests cover the behaviours above, written against **real objects** — a live
`capsfilter` and a real Unix socket — rather than mocks:

| test | what would break without it |
|---|---|
| `a_resize_rewrites_the_capsfilter_to_the_sanitised_size` | a resize that returns Ok and changes nothing |
| `an_out_of_range_request_is_clamped_and_the_caller_is_told_what_applied` | an out-of-range request reaching the encoder as a size it cannot represent |
| `a_second_resize_inside_the_window_is_refused_and_leaves_the_caps_alone` | a refused resize that applied anyway |
| `the_window_reopens_after_the_interval` | a rate limit that never lifts |
| `a_no_op_resize_is_not_rate_limited` | an idempotent retry reading as failure |
| `the_reply_names_what_applied_not_what_was_asked` | the socket echoing the request, re-creating the trap above |
| `a_client_can_bind_connect_and_get_a_reply_over_the_real_socket` | a module that passes its whole suite while no client can reach it |
| `bind_replaces_a_stale_socket_file` | `EADDRINUSE` after a crash, reading as "already running" when nothing is |
| `socket_path_is_overridable_so_a_second_instance_does_not_collide` | a test instance stealing the service's socket |

Three of these **failed on first run** — asserting the requested `900` — which is how the
round-to-8 finding above was discovered rather than shipped into a bed gate.

The last three were added in response to review: the first six covered `resize`/`dispatch` only, so
`bind`, `serve` and `handle` — the paths a resize actually arrives over — had no execution at all.

The check runs, inside the container:

```sh
printf 'resize 1600 900\n' | timeout 10 socat - UNIX-CONNECT:/tmp/cstream-control.sock
```

That reply cannot be produced unless the binary **bound the socket, spawned the serve thread, and
handled the connection** — the exact path under review — and then applied the resize and reported
the sanitised result. Both legs are identical, so it survives the destroy-and-rebuild.

It is also the first live confirmation of the round-to-8 finding: the request is `1600 900`, the
reply is `1600x896`.
