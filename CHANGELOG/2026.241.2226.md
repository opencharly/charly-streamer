# 2026.241.2226 — feat(leader): real PAM authentication, with the credential off argv

## Summary

The session leader gets the half that was missing: **real PAM authentication**, plus a CLI a bed
can drive. `crates/cstream-leader` already owned the privilege drop (#4); it had no way to decide
*whether* a login should happen at all, and no entry point, so nothing could execute it.

Three pieces:

1. **`authenticate_and_open()`** — `pam-client` 0.5, in the order the contract requires:
   `authenticate` → `acct_mgmt` → `putenv` → `open_session`. Each leg is separately fallible and
   separately named in the error.
   - `acct_mgmt` is **not** optional and is commented as such: a locked or expired account
     *authenticates successfully* and is refused only there, so skipping it admits disabled users.
   - `putenv` runs **before** `open_session` because logind reads `XDG_SESSION_CLASS` when the
     session is created; setting it afterwards has no effect and the `user@UID.service` tree — the
     thing that actually owns the desktop's units — never starts.
   - the returned `Session` guard is deliberately leaked (`std::mem::forget`): dropping it closes
     the session immediately, so a leader that discarded it would open and tear down in one step
     and logind would never see a live session.

2. **`src/bin/cstream-leader.rs`** — the CLI, with exit codes as the contract
   (`0` authenticated / `1` refused / `2` usage), printing `LEADER-AUTH-OK` or `LEADER-AUTH-FAIL`.

3. **The password is read from STDIN, never argv.** argv is world-readable through
   `/proc/<pid>/cmdline` for the process's whole lifetime, so a login leader taking the credential
   as an argument hands every password to any local account that runs `ps`. There is a live gate
   for this below, not just an assertion in a comment.

**4. One measured constraint the gate is shaped by, recorded because it is easy to get wrong.**
`pam_unix` delegates to the setuid helper `unix_chkpwd` whenever euid is not 0, and that helper
only verifies the **calling** user's own account. So in a rootless pod (exec identity uid 1000,
empty capability set) authenticating any *other* user fails with *"Authentication service cannot
retrieve authentication info"* **regardless of the password** — which would make both legs of a
login gate fail and a reject-leg pass for the wrong reason. Measured, including the dead end:

```
uid 1000 → another account : LEADER-AUTH-FAIL "cannot retrieve authentication info"  (both passwords)
uid 0    → another account : LEADER-AUTH-OK                                          (exit 0)
uid 1000 → its OWN account : LEADER-AUTH-OK / LEADER-AUTH-FAIL                       (discriminates)

cap_add CAP_DAC_READ_SEARCH → /etc/shadow readable, pam_unix STILL uses the helper → no fix
```

The bed therefore authenticates the account it runs as. Cross-user authentication — what the
production broker does, as root — is `check-cstream-vm`'s gate, per the plan.

**6. On `pam-sys 1.0.0-alpha5` (raised as a supply-chain note).**
`pam-client` 0.5 — the current release, and the only maintained safe Rust PAM wrapper — requires
`pam-sys 1.x`, and upstream has published 1.0 only as alphas. The alternatives are worse for a
security-critical surface: `pam` and `pam-auth` are unmaintained and wrap the same `libpam`;
calling `libpam` through hand-written FFI would put the conversation-callback lifetime and the
`Session` guard's drop semantics — the two things most likely to be got wrong here — in our own
code instead of a reviewed crate. `pam-sys` is a thin bindgen shim over the system `libpam`: it
adds no cryptography, no parsing and no network surface of its own, and the actual authentication
happens in the distro's `libpam` either way. The pin is exact in `Cargo.lock`, and the version is
recorded here so a future move to a stable 1.0 is a deliberate bump rather than a surprise.
