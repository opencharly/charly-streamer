# 2026.242.1112 — feat(streamer): become the Wayland parent — capture, tap and encode in one pipeline

## Summary

The streamer becomes the Wayland parent, which is what the architecture always said it was:
*"the streamer **is** the Wayland parent"*. Until now it ran **beside** a separate parent
pipeline, and that could not work.

`waylanddisplaysrc` creates a compositor **and holds the render node**, so a second one cannot
observe the first's display. A streamer running alongside a parent therefore captured its **own
empty compositor** while the desktop drew into the other: signalling negotiated a session
end-to-end and no media followed. Three independent routes reached the same conclusion -- that,
plus a pod that **died mid-run** with two long-lived GWD displays (19 checks lost to
`no container with name`), plus two streamers colliding on the fixed signalling port.

Three changes:

1. **`build_capture` gains the frame tap** (`tee` -> `videorate` -> `jpegenc` -> `multifilesink`),
   so one pipeline provides what two used to. Queues on **both** branches: without them a stalled
   tap back-pressures the encoder and the stream stutters for a reason unrelated to the stream.
2. **`prepare_runtime_dir`** creates `XDG_RUNTIME_DIR` before the compositor needs it.
3. **A PLAYING failure now reports the BUS error**, not just the operation.

## The diagnostic change is the one that mattered

`set_state` returns a bare `StateChangeError` naming nothing, so a startup failure read
`bringing the pipeline to PLAYING` and gave no way to tell a missing element from a caps failure
from a busy render node. **Six hypotheses died to measurement** before this was added. Draining
the bus turned that message into:

```
GstWaylandDisplaySrc: Panicked: called `Result::unwrap()` on an `Err` value: RecvError
```

-- GWD's compositor thread dying because `XDG_RUNTIME_DIR` did not exist. The old parent *script*
created it; replacing the script with this binary took over the pipeline and silently dropped the
setup. One commit turned a four-cycle mystery into a one-line finding, which is why it ships here
rather than being reverted as scaffolding.

`prepare_runtime_dir` only chmods a directory it **creates**: chmod on a pre-existing `/tmp` path
we do not own fails with EPERM and would kill the streamer before it does any work -- the parent
script carried the same warning in a comment.

## Change classification

**Change class:** product code (Rust) -- `pipeline.rs` (frame tap + test), `display.rs`
(`prepare_runtime_dir` + test), `main.rs` (runtime-dir call, tap wiring, bus-error reporting). No
new dependency, no schema, no Go, no workflow.

**Verification gate:** `check-cstream-pod` with the streamer as the parent service.

**Breaking change + rollback:** the streamer now owns the display rather than attaching to one.
Rollback returns to a configuration where nothing can consume the stream.

Two tests pin properties that would otherwise regress silently:

- **the tap must live in the SAME pipeline as the encoder branch** -- splitting it back out
  reintroduces the empty-compositor failure, where a content gate reads a display nobody draws into
- **a missing runtime dir is created 0700; an existing one is left untouched** -- both halves,
  because the first prevents the `RecvError` panic and the second prevents the EPERM

```

```

`cstream-stream-live` reads the frame tap this change adds, and the `wl-*` checks only find windows
because Hyprland nested into the streamer's own compositor -- so both halves of the restructure are
exercised, not merely present.

## What this does NOT claim

A consumer receiving decodable video. Signalling is proven end to end -- the producer registers, a
consumer registers as `[Consumer]`, `startSession` is sent and a session starts -- and then no
media follows, with no ICE/DTLS error surfacing. That is **no longer** the empty-compositor
problem: the frame tap proves this parent has real content. It is tracked as WP3d, and until it is
understood `cstream-frame-probe` is deliberately **not shipped** and `cstream: frame` is **not
offered** -- shipping a probe with no gate is what got `pod-cstream#5` blocked, correctly.

## Rulebook compliance

- **R0 -- skills honoured.** git-workflow, root-cause-analyzer.
- **R1 -- RCA every anomaly.** Six hypotheses were tested and **discarded**: storage-lock
  contention, unreaped images, a `plugin-wl` resolution shift, mixed-memory tee negotiation, and
  `Supported DMA formats: []` (which the *working* parent logs five times, so it is benign noise).
  The cause was found only after the binary was made to report its own bus error.
- **R2 -- nothing parked.** WP3d is not a deferral of this change's scope: it is a distinct, named
  gap with its evidence recorded, and nothing depending on it is shipped.
- **R3 -- no duplication.** One pipeline provides capture, tap and encode; the separate parent
  pipeline it replaces is retired in the sibling `pod-cstream` change.
- **R4 -- no workaround.** The runtime dir is created rather than assumed; the tap is a real branch
  rather than a second process reading a display it cannot see.
- **R5 -- delete legacy completely.** Handled in the sibling change, which repoints the service.
- **R6 -- git safety.** `git status` before each commit; `feat/` branch; no force-push; no direct
  push to `main`.
- **R7/R10 -- prove the gate on the final committed tree.** The bed is `disposable: true` and
  completes its destroy-and-rebuild leg.
